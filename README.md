# XHSearch — 小红书/抖音笔记评论监控，回写飞书多维表格

把「每条帖子都要手动点开看评论区」变成「表格里自己就是最新的」。

每行一篇已发布的笔记，机器定期去取：**评论数**、**置顶评论内容**、**综合排序前 8 条评论**，
判断帖子是否失效/被限流，并把结论写进 `流量状态` 多选字段——**不覆盖运营手工打的标签**。

---

## 一、先说三条做不到 / 会花钱的事

这三条决定要不要做、怎么做，放在最前面。

### 1. 抖音没有「置顶评论」这个能力

抖音评论接口返回的字段是：`comment_id / content / create_time / like_count / reply_count /
ip_location / image_urls / sticker / is_hot / is_folded / author`。

**没有 `is_pinned`**，只有"是否热评"和"是否折叠"；而且**没有 `sort_type` 参数**，排序不可控。

所以：

| 需求 | 小红书 | 抖音 |
|---|---|---|
| 评论数 | ✅ | ✅（需多调一次 detail 兜底） |
| 置顶评论内容 | ✅ | ❌ 接口无此字段 |
| 置顶成功判定 | ✅ | ❌ 接口无此字段 |
| 前 N 条评论 | ✅ 综合排序 | ⚠️ 平台默认序，口径与小红书不等价 |

代码里抖音行的 `置顶状态` 会如实写「抖音·不支持判定」，**不留空**——留空会被运营读成"没置顶"，
而真相是"这个接口根本看不到"。如果抖音的单子对客户承诺过置顶监控，这事要现在处理。

### 2. 一次调用 ¥0.10，成本主要由刷新频率决定

计费口径（官网核实）：列表/搜索/评论 **10 积分/页**，1 积分 = 0.01 元。
接口没有 `page_size` 参数，页大小服务端定（10–20 条），**取 3 条和取 20 条一个价**。

调用次数（接口 schema 核实）：

- **小红书 = 1 次**。评论接口一次同时返回 `comment_count`（笔记总评论数）、
  `is_pinned`（置顶就在第一页）、和综合排序的前一页评论。R1/R2/R3 一次拿全，**不需要额外调 detail**。
  只有想要点赞/收藏（爆文的另一个维度）时才补一次。
- **抖音 = 2 次**。评论接口的 `comment_count` 类型是 `integer|null`（"当前不可用时为 null"），
  为了"评论数"这列不间歇性变空，detail 必须恒定兜底。

按每天新发 20 条、留存 30 天、小红书七成算（`python3 tools/estimate_cost.py` 可自己改参数重算）：

| 策略 | 调用/天 | 月成本 | 最坏陈旧度 |
|---|---:|---:|---|
| **分层刷新（本项目默认）** | 639 | **¥1,918** | 新帖 8 小时 |
| 分层 + 关掉小红书 detail | 485 | ¥1,456 | 同上，但没有点赞/收藏 |
| 全表每天刷一遍 | 1,200 | ¥3,600 | 24 小时 |
| 纯手动点（按 15% 行被点到） | 126 | ¥378 | **无穷大** ⚠️ |

### 3. 「点一次刷一条」还是「刷全部」—— 两个都要，但主力不是按钮

这是你问的核心问题。答案是**分层自动刷新当主力，手动按钮当逃生口**，理由是钱和风险两头都站得住：

**成本上，"全表日刷"贵在没意义的地方。** 8–30 天那 460 条占在管总量的 77%，
在全表日刷里也吃掉 77% 的预算，而它们的数据几乎不动了。把这笔钱挪到新帖上，
花更少的钱换来更高的时效——这不是取舍，是同价位下的严格改进。

**纯手动的问题不在钱，在于最坏陈旧度是无穷大。** 没被点到的行永远不更新，
而**风控和封控恰恰是必须被动发现的事件**——靠运营记得去点，等于没有监控。

所以按钮的正确定位是三个具体场景：客户临时来问、疑似风控要复核、刚做完置顶要立刻验证。
代码里给按钮加了 **90 秒同行冷却**：有人连点 200 次 = 1 次真实调用。

## 二、架构

```
                    ┌──────────────────────────────────┐
   运营勾选          │      飞书多维表格（唯一的界面）      │
   「排队刷新」  ───▶ │  一行 = 一篇笔记                   │
                    │  流量状态 / 评论数 / 置顶评论 / 快照  │
                    └───────────┬──────────────────────┘
                                │ 读表 + 写回（开放平台 API）
                                ▼
                    ┌──────────────────────────────────┐
                    │  本项目（扣子代码节点 或 小服务）      │
                    │  链接识别 → 调接口 → 判定 → 合并标签   │
                    └───────────┬──────────────────────┘
                                │ REST（纯 JSON）
                                ▼
                    ┌──────────────────────────────────┐
                    │  SocialDataX                      │
                    │  /api/v1/{xhs,douyin}/.../list    │
                    └──────────────────────────────────┘
```

### 中间层是必需的，不是选择

飞书自动化的「发送 HTTP 请求」节点**没法自己完成这件事**，原因是它取不出数组里的元素。

要填「置顶评论」这一列，必须求值 `items[?is_pinned].content`。而飞书 HTTP 节点
只能整体引用数组，无法引用数组里的单个变量；循环节点也堵死了——循环体内不支持条件判断
（没法筛 `is_pinned`），循环结束后的节点又引用不到循环内的数据（没法攒前 N 条）。
**在飞书内部把数组拍平在结构上就做不到**，必须有个东西把数组变成标量。

这就是这个中间层存在的全部理由。它不需要 LLM，不需要状态，就是取数 → 拍平 → 判定 → 写回。

（顺带一提：走 MCP 端点的话还有第二个障碍——那条路的成功响应是 SSE 分帧，
而飞书 HTTP 节点靠"粘一段 JSON 样例"解析响应，喂 SSE 进去解不出来。
本项目改用 REST 端点后没这个问题，但拍平数组的问题依然在。）

### 接口用的是 REST，不是 MCP

同一个后端、同样的字段，但 REST 明显更好：

- **纯 JSON**，不用处理 SSE 分帧，也不用小心翼翼地拼 `Accept` 头
- **有一份公开可读、不需要 Key 的 OpenAPI 3.1 规范**，带完整错误码契约：
  `https://api.52choujiang.cn/socialdatax/api/v1/docs/openapi.json`

⚠️ 这个接口有一处很容易写错的地方：**业务错误也返回 HTTP 200**，
靠 body 里有没有 `code` 字段区分（规范原文：「请求成功；业务错误也会返回 200 + {code, message}。」）。
只看 HTTP 状态码的客户端，会把每一个「笔记已删除」当成成功。

错误码是权威的，不需要猜中文话术：

| code | 含义 | 处置 |
|---:|---|---|
| 1003 | 不存在或不可见 | 两击定罪 → 已失效 |
| 1006 | 权限/状态/平台限制导致不可读 ← **封控** | 两击定罪 → 已失效 |
| 1007 | 页面暂时不可访问 | 退避重试，**不判失效** |
| 1008 | 已删除（规范明写"不要重试"） | **第一次就定罪** |
| 1004 | 积分不足 | 整批停 |
| 1401 / 1429 | Key 无效 / 限流 | 整批停 / 按 `retry_after_seconds` 退避 |

`1007`（页面暂时打不开）和 `1006`（内容被限制）分开处置这一点很关键——
混为一谈就会把瞬时故障标成风控。

### 触发通道

| 通道 | 怎么触发 | 飞书自动化配额 | 用途 |
|---|---|---|---|
| **A · 勾选 + 轮询** | 运营勾 `排队刷新`，后台每分钟扫表 | **0 次** | 主力手动入口，可拖拽批量勾 |
| **B · 分层巡检** | 后台定时任务 | **0 次** | 基线覆盖，风控/封控靠它发现 |
| **C · 按钮字段** | 点按钮 → 自动化 → HTTP | **每次点击 1 次** | 秒级响应的急查口 |

⚠️ **飞书自动化运行次数是按月、按租户共享的配额**（各版本从 200 次/月到 50 万次/月不等，
自动化和工作流共用）。如果你们是较低档位，按钮点几百次就会把**全公司**的自动化额度
（合同、报销、排期）一起打光，而且失败模式是**静默停摆**——表不报错，只是不更新。

**所以通道 A 才是主力**：它一次配额都不消耗，体验上和按钮差别只有"要等最多一分钟"。
勾选还能拖拽批量勾 50 行，按钮只能一行一行点。处理完机器会自动把勾去掉——**勾消失就是"已完成"**，
不需要向运营解释任何东西。

## 三、跑在哪：扣子 vs 一台小服务

你倾向扣子。**扣子能跑，我不推翻**，但有一件事要先讲清楚：

> **选扣子并不能让你少写 Python，只能让你在更差的编辑器里写同样的 Python。**

因为扣子代码节点**能联网**（内置 `requests_async`），所以完全可以在一个代码节点里跑完整套逻辑。
但如果把每条笔记展开成工作流节点，600 行会撞上节点执行上限——**必须把循环写在 Python 里**。
既然逻辑无论如何都是 Python，区别就只剩下它住在哪。

| | 扣子代码节点 | 一台小服务 |
|---|---|---|
| 托管 cron + HTTPS 入口 | ✅ 自带 | 要自己配 |
| 代码节点硬上限 | **60 秒**，600 行必须切成 15 块 | 无，一口气跑完约 7 分钟 |
| 版本管理 / diff / 单测 | ❌ 网页 textarea | ✅ git |
| 本地调试 | ❌ 只能看网页运行记录 | ✅ |
| 月成本 | 可能需付费版解锁定时触发 | ¥24 左右 |

**本项目两边都支持，逻辑只有一份**：

- 独立服务 / 本地定时任务 → 直接 `python3 cli.py sweep`
- 扣子 → `python3 tools/build_coze_node.py > coze_node.py`，把生成的文件粘进代码节点

打包脚本从同一份源码生成，所以**不会出现"白天点按钮和夜里批量跑结论不一致"**——
那是这类系统里最难查也最伤信任的一类 bug。`tests/test_coze_bundle.py` 会把打包产物
真的 exec 起来跑一遍，防止打包时剥错 import。

## 四、防止写坏表的三处设计

这是整个项目里最该被理解的部分。运营对表的信任一旦丢了就补不回来。

### 1. 标签合并：人工标签永远不动

飞书多选字段的写入是**整体覆盖**，没有原子 append。所以必须读-改-写：

```
新值 = (现有标签 − 机器命名空间) ∪ (本次算出的标签)
```

机器只认 `爆文 / 风控 / 预警 / 置顶成功 / 已失效` 这五个词，其余一切
（`已复盘`、`客户确认`，以及运营未来新增的任何选项）**机器零权限**。

标签还分两类：`爆文` 是**粘性**的（爆过就是爆过，回落不代表没爆过，要摘由人工摘）；
`风控 / 预警 / 置顶成功` 是**易变**的（每轮重算，恢复正常自动摘掉，否则表会越来越红）。

**无变化就根本不写这个字段**——省一次写，也不让人看到这行被反复改动。

### 2. 两击定罪：一次失败不判死

一次网络抖动或上游话术改版，就把好帖子标成"风控"，运营会全线停投。

所以第一次取不到内容只写「疑似受限」并计数，**一个标签都不打**；连续两次才判「已失效」。
任何一次成功都会把计数器清零。

### 3. 全局熔断：批量失效 = 上游故障，不是内容出事

一批里判定失效的比例超过 20%（且样本 ≥ 10 行）→ **整批撤销标签写入**。

几百条笔记不可能在同一小时里被集体删除。真出现这种情况，一定是上游挂了或者错误话术改版了。
宁可这一轮什么都不写。

另外：**任何失败路径都不清空数据列**。`评论数`、`置顶评论`、`评论区快照` 保留上一次的成功值——
清成 0 会制造"爆文突然归零"的假警报。

## 五、快速开始

```bash
# 1. 配置（复制后填写）
cp .env.example .env && vim .env

# 2. 体检：不花一分钱，检查权限/字段/选项是否齐全
set -a && source .env && set +a
python3 cli.py doctor

# 3. 只估算这一轮要花多少钱，不发请求
python3 cli.py estimate

# 4. 真跑
python3 cli.py sweep          # 分层巡检：只刷到期的行
python3 cli.py queue          # 只刷勾了「排队刷新」的行
python3 cli.py row recXXXX    # 刷指定行（无视冷却和分层节流）

# 测试（全离线，不需要 API Key）
python3 -m unittest discover -s tests -t .
```

建表步骤见 [`docs/表结构.md`](docs/表结构.md)。

## 六、上线前必须验的事

代码里有几处是**按合理推测写的防御逻辑**，因为当前环境没有 API Key，验不了。
拿到 Key 后照 [`docs/待验证清单.md`](docs/待验证清单.md) 跑一遍，**总花费不到 ¥10**。

其中最要紧的一条：**「笔记被删」实际会命中哪个错误码**。规范定义了 `1003 / 1006 / 1008`
三个都可能对应"取不到内容"，但没说小红书笔记被删时具体返回哪个。这三个在代码里的处置不同
（`1008` 第一次就定罪，另两个走两击），所以必须拿几条真实的已删笔记跑一遍才能定标。

## 七、代码结构

```
xhsearch/
  links.py       链接识别：判平台、抽 ID。纯函数，不发请求
  protocol.py    接口协议：组包、解包、官方错误码归类。纯函数
  analyze.py     评论页 → 指标/置顶状态/快照文本/标签判定。纯函数
  tags.py        多选字段合并算法。纯函数
  rows.py        行模型 + 调用计划（这里决定花多少钱）。纯函数
  config.py      列名映射与判定口径 ← 唯一需要按你们表结构改的文件
  transport.py   HTTP（标准库，零依赖）
  feishu.py      多维表格读写
  runner.py      编排：读表 → 调接口 → 判定 → 写回
cli.py           命令行入口
tools/
  build_coze_node.py   打包成扣子代码节点用的单文件
  estimate_cost.py     按配置算月度成本
tests/           122 个测试，全离线
```

分层的用意：**纯函数和网络严格分开**。所以核心逻辑能整段打包进扣子，
也能在本地毫秒级跑完全部测试，不需要任何 Key。
