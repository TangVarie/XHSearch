# XHSearch — 小红书/抖音笔记评论监控，回写飞书多维表格

> 📦 **代码已经搬到 <https://github.com/TangVarie/linkcheck> 了，以后在那边维护。**
> 那个仓库是干净的一条提交、默认分支 `main`、Railway 直接连它。
> 这个仓库留作归档，另外 `.claude/skills/` 下那 8 个 SocialDataX skill 只在这里有
> （它们是给交互式调研用的 MCP skill，跟监控服务无关，所以没搬过去）。

把「每条帖子都要手动点开看评论区」变成「表格里自己就是最新的」。

每行一篇已发布的笔记，机器定期去取：**评论数**、**置顶评论内容**、**综合排序前 8 条评论**，
判断帖子是否失效/被限流，并把结论写进 `流量状态` 多选字段——**不覆盖运营手工打的标签**。

## 一、先说三条做不到 / 会花钱的事

这三条决定要不要做、怎么做，放在最前面。

### 1. 抖音没有「置顶评论」这个能力

SocialDataX 的抖音评论接口返回：`comment_id / content / create_time / like_count /
reply_count / ip_location / image_urls / sticker / is_hot / is_folded / author`——
**没有 `is_pinned`**，只有"是否热评"和"是否折叠"；而且**没有 `sort_type` 参数**，排序不可控。

TikHub 那边是上游原始透传，条目里多了 `label_type` / `label_text`，
**看着像置顶标记但语义没验过**。代码里一律不判抖音置顶——
错判置顶比不判置顶伤害大得多。要验的话见 [`docs/待验证清单.md`](docs/待验证清单.md) 第 18 项，
成本 ¥0.007。

所以：

| 需求 | 小红书 | 抖音 |
|---|---|---|
| 评论数 | ✅ | ✅（需多调一次 detail 兜底） |
| 置顶评论内容 | ✅ | ❌ 接口无此字段 |
| 置顶成功判定 | ✅ | ❌ 接口无此字段 |
| 前 N 条评论 | ✅ 综合排序 | ⚠️ 平台默认序，口径与小红书不等价 |

代码里抖音行的 `置顶评论` 会如实写「—（抖音不支持置顶监控）」，**不留空**——
留空会被运营读成"没置顶"，而真相是"这个接口根本看不到"。
`评论状态` 那一列抖音行**完全不碰**，写任何值都是撒谎。

### 2. 成本主要由刷新频率决定，其次才是走哪家

**双通道**：默认优先 TikHub，SocialDataX 兜底。单价差得很多：

| | 小红书 | 抖音 |
|---|---:|---:|
| TikHub（主） | ¥0.072/次 | **¥0.0072/次** |
| SocialDataX（备） | ¥0.10/次 | ¥0.10/次 |

抖音便宜 93%，小红书便宜 28%，整体省一半。完整对比和踩到的坑见
[`docs/供应商对比.md`](docs/供应商对比.md)。

接口都没有 `page_size` 参数，页大小服务端定（10–20 条），**取 3 条和取 20 条一个价**。

调用次数（实测核实）：

- **小红书 = 1 次**。评论接口一次同时返回 `comment_count`（笔记总评论数）、
  `is_pinned`（置顶就在第一页）、和综合排序的前一页评论。R1/R2/R3 一次拿全，**不需要额外调 detail**。
  只有想要点赞/收藏（热度判定的另一个维度）时才补一次。
- **抖音 = 2 次**。SocialDataX 的 `comment_count` 类型是 `integer|null`（"当前不可用时为 null"），
  为了"评论数"这列不间歇性变空，detail 必须恒定兜底。
  （TikHub 的 `total` 实测是实数，但 detail 还要拿点赞收藏，照调。抖音一次才 ¥0.007，无所谓。）

按每天新发 20 条、留存 30 天、小红书七成算（`python3 tools/estimate_cost.py` 可自己改参数重算）：

| 策略 | 调用/天 | 月成本（TikHub） | 月成本（SocialDataX） | 最坏陈旧度 |
|---|---:|---:|---:|---|
| **分层刷新（本项目默认）** | 639 | **¥946** | ¥1,918 | 新帖 8 小时 |
| 分层 + 关掉小红书 detail | 485 | ¥796 | ¥1,456 | 同上，但没有点赞/收藏 |
| 全表每天刷一遍 | 1,200 | ¥1,892 | ¥3,600 | 24 小时 |
| 纯手动点（按 15% 行被点到） | 126 | ¥186 | ¥378 | **无穷大** ⚠️ |

### 3. 「点一次刷一条」还是「刷全部」—— 两个都要，但主力不是按钮

这是你问的核心问题。答案是**分层自动刷新当主力，手动按钮当逃生口**，理由是钱和风险两头都站得住：

**成本上，"全表日刷"贵在没意义的地方。** 8–30 天那 460 条占在管总量的 77%，
在全表日刷里也吃掉 77% 的预算，而它们的数据几乎不动了。把这笔钱挪到新帖上，
花更少的钱换来更高的时效——这不是取舍，是同价位下的严格改进。

**纯手动的问题不在钱，在于最坏陈旧度是无穷大。** 没被点到的行永远不更新，
而**风控和封控恰恰是必须被动发现的事件**——靠运营记得去点，等于没有监控。

所以按钮的正确定位是三个具体场景：客户临时来问、疑似风控要复核、刚做完置顶要立刻验证。
代码里给按钮加了 **90 秒同行冷却**：有人连点 200 次 = 1 次真实调用。

## 二、架构

```
                    ┌──────────────────────────────────┐
   运营勾选          │      飞书多维表格（唯一的界面）      │
   「排队刷新」  ───▶ │  一行 = 一篇笔记                   │
                    │  流量状态 / 评论数 / 置顶评论 / 快照  │
                    └───────────┬──────────────────────┘
                                │ 读表 + 写回（开放平台 API）
                                ▼
                    ┌──────────────────────────────────┐
                    │  本项目（扣子代码节点 或 小服务）      │
                    │  链接识别 → 调接口 → 判定 → 合并标签   │
                    └───────────┬──────────────────────┘
                                │ 双通道，主挂了自动降级
                    ┌───────────┴───────────┐
                    ▼                       ▼
        ┌────────────────────┐  ┌────────────────────────┐
        │ TikHub（主）        │  │ SocialDataX（备）        │
        │ GET + query        │  │ POST + JSON            │
        │ api.tikhub.dev     │  │ mcp.socialdatax.com    │
        └────────────────────┘  └────────────────────────┘
```

两家的响应形状完全不同（一家是上游原始透传，一家是归一化过的），
差异全部挡在 [`xhsearch/providers.py`](xhsearch/providers.py) 一层里，
判定逻辑只认一种形状。

### 中间层是必需的，不是选择

飞书自动化的「发送 HTTP 请求」节点**没法自己完成这件事**，原因是它取不出数组里的元素。

要填「置顶评论」这一列，必须求值 `items[?is_pinned].content`。而飞书 HTTP 节点
只能整体引用数组，无法引用数组里的单个变量；循环节点也堵死了——循环体内不支持条件判断
（没法筛 `is_pinned`），循环结束后的节点又引用不到循环内的数据（没法攒前 N 条）。
**在飞书内部把数组拍平在结构上就做不到**，必须有个东西把数组变成标量。

这就是这个中间层存在的全部理由。它不需要 LLM，不需要状态，就是取数 → 拍平 → 判定 → 写回。

（顺带一提：走 MCP 端点的话还有第二个障碍——那条路的成功响应是 SSE 分帧，
而飞书 HTTP 节点靠"粘一段 JSON 样例"解析响应，喂 SSE 进去解不出来。
本项目改用 REST 端点后没这个问题，但拍平数组的问题依然在。）

### SocialDataX 那条通道用的是 REST，不是 MCP

同一个后端、同样的字段，但 REST 明显更好：

- **纯 JSON**，不用处理 SSE 分帧，也不用小心翼翼地拼 `Accept` 头
- **有一份公开可读、不需要 Key 的 OpenAPI 3.1 规范**，带完整错误码契约：
  `https://api.52choujiang.cn/socialdatax/api/v1/docs/openapi.json`

⚠️ 这个接口有一处很容易写错的地方：**业务错误也返回 HTTP 200**，
靠 body 里有没有 `code` 字段区分（规范原文：「请求成功；业务错误也会返回 200 + {code, message}。」）。
只看 HTTP 状态码的客户端，会把每一个「笔记已删除」当成成功。

错误码是权威的，不需要猜中文话术：

| code | 含义 | 处置 |
|---:|---|---|
| 1003 | 不存在或不可见 | 两击定罪 → 已失效 |
| 1006 | 权限/状态/平台限制导致不可读 ← **封控** | 两击定罪 → 已失效 |
| 1007 | 页面暂时不可访问 | 退避重试，**不判失效** |
| 1008 | 已删除（规范明写"不要重试"） | **第一次就定罪** |
| 1004 | 积分不足 | 整批停 |
| 1401 / 1429 | Key 无效 / 限流 | 整批停 / 按 `retry_after_seconds` 退避 |

`1007`（页面暂时打不开）和 `1006`（内容被限制）分开处置这一点很关键——
混为一谈就会把瞬时故障标成风控。

**TikHub 那条通道没有这张表**——它没有公开的业务错误码契约，失效判定只能靠
响应形状的启发式（空壳判活、detail 的 `data: []`、抖音的 `filter_list`）。
这是它唯一明显不如 SocialDataX 的地方，也是后者值得留着当备胎的理由。
详见 [`docs/供应商对比.md`](docs/供应商对比.md) 第三节。

### 触发通道

| 通道 | 怎么触发 | 飞书自动化配额 | 用途 |
|---|---|---|---|
| **A · 勾选 + 轮询** | 运营勾 `排队刷新`，后台每分钟扫表 | **0 次** | 手动入口，可拖拽批量勾 |
| **B · 分层巡检** | 后台定时任务 | **0 次** | 基线覆盖，风控/封控靠它发现 |
| ~~C · 按钮字段~~ | ~~点按钮 → 自动化 → HTTP~~ | ~~每次点击 1 次~~ | **不建议用，见下** |

**这个方案不用按钮字段，也因此不需要升级飞书套餐。**

飞书自动化运行次数是**按月、按租户共享**的配额，自动化和工作流共用。
当前套餐 200 次/月 ÷ 30 天 ≈ **每天 6.7 次**——几百条帖子的规模，
按钮点两下就没了。而且失败模式是**静默停摆**：表不报错，只是不更新，
更糟的是它会把**全公司**的自动化额度（合同、报销、排期）一起打光。

通道 A 是它的完整替代：**一次配额都不消耗**，体验差别只有"最多等一分钟"，
而且能拖拽批量勾 50 行，按钮反而只能一行一行点。处理完机器自动把勾去掉——
**勾消失就是"已完成"**，不需要向运营解释任何东西。

升级套餐的钱花在数据接口上更值。

## 三、跑在哪

零依赖、纯标准库，所以哪都能跑：**Railway / 扣子 / GitHub Actions / 自建 VPS**
都是一条命令的事。完整步骤见 [`docs/部署.md`](docs/部署.md)，这里只说结论。

**推荐 Railway** → 手把手步骤见 [`docs/Railway上线手册.md`](docs/Railway上线手册.md)。

两条理由：

1. **双通道在扣子上可能用不上。** TikHub 挂在 Cloudflare 后面，请求必须带浏览器
   `User-Agent`（实测踩过，不带直接 403）。扣子的 `requests_async` 允不允许覆盖这个头
   **没有文档保证**——不允许的话扣子上就只剩一条通道，等于没有兜底。
2. **它直接连 git 仓库部署。** 扣子上跑的是**一份粘贴的副本**，改了源码忘了重新粘，
   表面上什么都看不出来——表还在更新、数字还在变，只是判定口径停在你改之前。
   这套东西每天往表里写几百次、运营完全依赖它，"跑的是哪一版"必须是确定的。

扣子的优势是境内 + 触发器 1 分钟（勾选响应最快），代价是 60 秒硬上限
（600 行要分 15 轮、约 30 分钟排干）、跑不了 `doctor`。

| | 扣子 | Railway | GitHub Actions | 自建 VPS |
|---|---|---|---|---|
| 勾选后多久有反应 | 1–2 分钟 | 5–10 分钟 | 10–70 分钟 | 1 分钟 |
| 代码从哪来 | ⚠️ 网页粘贴 | ✅ git 仓库 | ✅ git 仓库 | ✅ git 仓库 |
| 单次执行上限 | ⚠️ 60 秒 | 无 | 6 小时 | 无 |
| 服务器位置 | 境内 | 境外 | 境外 | 可选 |

要跑在扣子上：`python3 tools/build_coze_node.py > coze_node.py`，把生成的文件粘进代码节点。
打包脚本从同一份源码生成，`tests/test_coze_bundle.py` 会把产物真的 exec 起来跑一遍，
防止打包时剥错 import——但**它防不住"你改完代码忘了重新粘"**，那是扣子方案的固有风险。

## 四、防止写坏表的三处设计

这是整个项目里最该被理解的部分。运营对表的信任一旦丢了就补不回来。

### 1. 标签合并：人工标签永远不动

飞书多选字段的写入是**整体覆盖**，没有原子 append。所以必须读-改-写：

```
新值 = (现有标签 − 机器命名空间) ∪ (本次算出的标签)
```

机器只认 `评估中 / 爆贴 / 大爆 / 风控中 / 已失效` 这五个词，其余一切
（`已复盘`、`客户确认`，以及运营未来新增的任何选项）**机器零权限**。

热度三档（≥20 评估中，≥50 爆贴，≥100 大爆）**互斥且只升不降**：
每轮只留最高的一个；评论被删导致数字掉下去不该让帖子从「大爆」退回「爆贴」，
那种情况由 `风控中` 表达。`风控中 / 已失效` 是易变的，每轮重算，
恢复正常自动摘掉，否则表会越来越红。

**无变化就根本不写这个字段**——省一次写，也不让人看到这行被反复改动。

### 2. 两击定罪：一次失败不判死

一次网络抖动或上游话术改版，就把好帖子标成"风控"，运营会全线停投。

所以第一次取不到内容只写「疑似受限」并计数，**一个标签都不打**；连续两次才判「已失效」。
任何一次成功都会把计数器清零。

### 3. 全局熔断：批量失效 = 上游故障，不是内容出事

一批里判定失效的比例超过 20%（且样本 ≥ 10 行）→ **整批撤销标签写入**。

几百条笔记不可能在同一小时里被集体删除。真出现这种情况，一定是上游挂了或者错误话术改版了。
宁可这一轮什么都不写。

另外：**任何失败路径都不清空数据列**。`评论数`、`置顶评论`、`评论区快照` 保留上一次的成功值——
清成 0 会制造"爆贴突然归零"的假警报。

## 五、快速开始

```bash
# 1. 配置（复制后填写）
cp .env.example .env && vim .env

# 2. 体检：不花一分钱，检查权限/字段/选项是否齐全

python3 -m unittest discover -s tests -t .
```

## 七、代码结构

```
xhsearch/
  links.py       链接识别：判平台、抽 ID。纯函数，不发请求
  protocol.py    SocialDataX 协议：组包、解包、官方错误码归类。纯函数
  providers.py   双通道：两家的组包/归一化/错误分类都挡在这一层。纯函数
  analyze.py     评论页 → 指标/置顶状态/快照文本/标签判定。纯函数
  tags.py        多选字段合并算法。纯函数
  rows.py        行模型 + 调用计划（这里决定花多少钱）。纯函数
  config.py      列名映射与判定口径 ← 唯一需要按你们表结构改的文件
  transport.py   HTTP（标准库，零依赖）
  feishu.py      多维表格读写
  runner.py      编排：读表 → 调接口 → 判定 → 写回
cli.py           命令行入口
coze_node.py     ← 扣子代码节点直接粘这个（自动生成，CI 保证与源码同步）
tools/
  build_coze_node.py   生成上面那个文件
  estimate_cost.py     按配置算月度成本（两家分开报）
  probe_channel.py     拿一条真实链接把某条通道走一遍（会真扣费）
tests/           190 个测试，全离线
```
