# SocialDataX vs TikHub（已实测）

> **结论：TikHub 能干全套，已做成双通道。**
> 默认两个平台都优先 TikHub，SocialDataX 兜底。月成本 ¥1,918 → ¥946。
>
> 之前那份对比里最大的未知项——「TikHub 的小红书评论接口到底有没有置顶标记」——
> 已经用真 Key 打通验完了：**有，但不叫 `is_pinned`**。

本文所有数字都有出处。标「实测」的是 2026-08 用真 Key 直接打接口拿到的，
标「文档」的是对方公开文档原文。没有一条是估的。整轮验证总共花了 **$0.18（约 ¥1.3）**。

---

## 一、最关键的那个字段：找到了

TikHub 的 OpenAPI 把评论接口的响应声明成一个**无字段约束的通用对象**，
所以光读文档永远读不出它有没有置顶标记。实测打开发现：它是**上游原始响应的透传**，
置顶信息在里面，只是名字完全不同。

```json
"show_tags_v2": [
  {"style_id": "red", "type": "user_top",  "pos": "cmt_bottom", "text": "Pinned"},
  {"text": "Author", "pos": "post_name", "type": "is_author", "style_id": "red"}
]
```

| 我们要的 | SocialDataX | TikHub（实测） |
|---|---|---|
| 置顶标记 | `is_pinned: true` | `show_tags_v2[].type == "user_top"` |
| 作者本人评论 | `is_author_comment` | `show_tags_v2[].type == "is_author"` |
| 评论总数 | `comment_count` | `comment_count`（含楼中楼）+ `comment_count_l1`（只算一级） |
| IP 属地 | 中文 | **英文**（"Shanghai"），已在归一化层翻回中文 |
| 排序 | `sort_type=default` | `sort_strategy=default`，响应还回显 `current_sort_strategy` 可校验 |

⚠️ **认 `type` 不要认 `text`**：`text` 实测返回的是英文 "Pinned" / "Author"，
账号或地区一变就可能变成中文，认它迟早出事。

这些差异全部挡在 [`xhsearch/providers.py`](../xhsearch/providers.py) 一层里，
`analyze.py` 一行都没改。

## 二、钱：省一半，但省的地方不在小红书

TikHub 有一个**公开、免鉴权**的按端点计价接口（实测可直接 GET，1401 个端点）：

```
https://api.tikhub.dev/api/v1/tikhub/user/get_all_endpoints_info
```

| 端点 | 单价 | 走量折扣 | 免费额度可用 |
|---|---:|:---:|:---:|
| `xiaohongshu/app_v2/get_note_comments` | **$0.010** | ❌ | ❌ |
| `xiaohongshu/app_v2/get_image_note_detail` | **$0.010** | ❌ | ❌ |
| `douyin/app/v3/fetch_video_comments` | **$0.001** | ✅ | ✅ |
| `douyin/app/v3/fetch_one_video` | **$0.001** | ✅ | ✅ |

对照 SocialDataX：**¥0.10/次，全平台一个价**（10 积分 × ¥0.01）。

两件事要划重点：

1. 官网上那个「日调用量 1000 起阶梯折扣」，**对小红书接口不生效**（`allow_discount = 0`）。
   我们 65% 的调用量正好全压在小红书上。
2. 小红书接口 **`allow_free_credit = 0`**，每日签到送的免费额度用不到它。

### 按我们真实的分层刷新算（`python3 tools/estimate_cost.py 20 0.7`）

| | 小红书 415 次/天 | 抖音 224 次/天 | 合计/月 |
|---|---:|---:|---:|
| SocialDataX | ¥1,245 | ¥672 | **¥1,918** |
| TikHub | ¥896 | ¥48 | **¥946** |
| 省 | 28% | **93%** | **51%（¥972/月）** |

汇率按 1 USD = 7.2 CNY，7.0～7.5 之间都是省 49%～52%。

**「省一半」这个总数，一多半是抖音贡献的。** 小红书那段只便宜 28%——
这就是为什么 SocialDataX 值得留着当备胎而不是直接销号：它贵得不算离谱，
但在下面这件事上明显更强。

## 三、失效检测：TikHub 更脏，但够用

这是 TikHub 最弱的一环，也是我们花最多力气挡住的一环。

### 3.1 ⚠️ 传错笔记 ID 照样扣费（对方文档 + 实测双重确认）

> 如果传入错误或不存在的笔记ID，接口仍会正常响应，但 `data` 中会返回上游"服务异常"
> 信息，该请求 **同样会正常计费扣费**。 —— TikHub 接口文档原文

实测更糟：不存在的笔记返回的不是什么"服务异常"，而是一个**看起来完全正常的空壳**：

```json
{"code": 0, "success": true, "msg": "",
 "data": {"comments": [], "comment_count": 0,
          "all_sort_strategies": [],     // ← 活笔记这里有 3 个
          "user_id": ""}}                // ← 活笔记这里是作者 id
```

HTTP 200、`success: true`、没有任何错误信息，**而且扣了 $0.01**。
和「一条真实存在但零评论的新笔记」几乎一模一样。

对比 SocialDataX：`1006 content_unavailable`（封控）、`1008 content_deleted`
（厂商自己标了"不要重试"），语义和处置都写在公开规范里。

**我们的处理**：拿 `user_id` 和 `all_sort_strategies` 当线索判**嫌疑**，
但因为这是启发式而不是厂商契约，**绝不 definitive**——必须走满两击定罪。
账也照实记：`_was_billed()` 会把这类「HTTP 成功、业务失败」的调用算进成本，
只记成功的调用会让账面比账单少。

### 3.2 但 detail 接口的死亡信号是干净的（实测）

| 平台 | 活的 | 死的 |
|---|---|---|
| 小红书 `get_image_note_detail` | `data: [{note_list: [{...}]}]` | **`data: []`** |
| 抖音 `fetch_one_video` | `aweme_detail: {...}` | **`aweme_detail: null` + `filter_list: [{aweme_id, reason: 8}]`** |

这两个是确定性的，代码里一次定罪，不用等第二轮。

⚠️ 但有一条护栏：**评论接口刚拿回一堆评论、detail 却说笔记不存在时，不认 detail**。
那是上游自相矛盾，信它就是拿一次抖动杀掉一条好帖子。见
`runner._looks_alive()` 和 `tests/test_failover.py::test_live_note_is_not_killed_by_a_contradictory_detail`。

### 3.3 顺带白捡的：上游自己的审核标记

| 平台 | 字段 |
|---|---|
| 小红书 detail | `in_censor` |
| 抖音 detail | `status.is_prohibited` / `status.in_reviewing` |

SocialDataX 没有这两个。**目前只写进「诊断信息」提醒人看，不参与打标签**——
只见过 `false`，语义没在真被封的帖子上验过，凭没验过的字段打「风控中」，
一旦误报就是运营全线停投。验过之后再提升，见 [`待验证清单.md`](待验证清单.md)。

## 四、三个实测踩出来的坑（都已在代码里处理）

### 4.1 不带浏览器 UA 直接 403

裸 urllib 的默认 UA 会被 Cloudflare 判成机器人：

```
HTTP 403  {"error_code": 1010, "error_name": "browser_signature_banned"}
```

连业务层都到不了。SocialDataX 裸 urllib 就能通。

处理：`providers.py` 里写死了浏览器 UA，并且**把 Cloudflare 的 403 归类成
TRANSPORT 而不是 AUTH**——归成 AUTH 会把这条通道整轮标死，可它换个网络就好了。

### 4.2 报错信息会把你的 API Key 原样回显

实测（用假 Key 打的）：

```json
{"detail": {"code": 401, "message_zh": "无效的API令牌，您提交的API令牌为 <你的key>。..."}}
```

我们的 runner 会把错误文案写进飞书的「诊断信息」列。照抄就等于**把 Key 写进表里给全公司看**。

处理：`_redact()` 在落库前抹掉，`tests/test_failover.py::TestSecrets` 钉死这条。

### 4.3 主域名在大陆被墙

对方文档原文：`api.tikhub.io` 被防火墙拦截，大陆用户须用 **`api.tikhub.dev`**
（实测该域名可用，同一套接口、同一套鉴权）。

处理：`TIKHUB_BASE` 写死成 `.dev`，测试里钉死免得被人改回去。

## 五、双通道怎么工作

```
                    ┌─ 主通道 TikHub ──── 成功 ──▶ 归一化 ──▶ 判定
调用 ──▶ 选通道 ──┤
                    └─ 网络故障 / Key 失效 / 余额耗尽 ──▶ 降到 SocialDataX
```

配置在 [`xhsearch/config.py`](../xhsearch/config.py) 的 `Channels`：

```python
order = {"xhs": ["tikhub", "socialdatax"], "douyin": ["tikhub", "socialdatax"]}
```

只想用一家就写成单元素，或者用环境变量 `CHANNEL_ORDER=xhs=socialdatax; douyin=tikhub`。
**没配 Key 的那家会自动从顺序里滤掉**，所以只填一个 Key 也能直接跑。

三条规则，每条都有测试钉着：

1. **只有通道故障才降级**（TRANSPORT / AUTH / QUOTA）。
   **「笔记没了」绝不降级**——那是行级结论，换一家只会再花一次钱得到同一个答案。
2. **Key 失效 / 余额耗尽 = 整轮拉黑这家**，不是每行都去撞一次 401。
   600 行各撞一次既慢又会把限流打出来。
3. **所有通道都倒下才算致命**。这正是双通道最值钱的地方：
   以前半夜 Key 失效 = 一整晚的监控全丢，现在只是换一家继续跑。

## 六、还没验的

见 [`待验证清单.md`](待验证清单.md)。和双通道相关的三条：

1. **TikHub 余额耗尽时到底返回什么** —— 现在靠 HTTP 402/403 + 「余额/充值/insufficient」
   文案兜。对方没有公开的业务错误码表（SocialDataX 有）。
2. **`in_censor` / `is_prohibited` 在真被封的帖子上是不是 true** —— 验了才敢拿它打标签。
3. **抖音的置顶** —— 评论里有 `label_type` / `label_text`，但语义没验过，
   现在一律不判置顶（和之前对你的承诺一致）。
