# SocialDataX vs TikHub

> 结论先放：**现在别整体换。** 抖音那部分可以马上换，省得明明白白；
> 小红书那部分能不能换，取决于一个我查不到、只能你花 ¥0.07 实测的字段。
> 实测脚本：[`tools/probe_tikhub.py`](../tools/probe_tikhub.py)

本文所有数字都有出处，标了「实测」的是我 2026-08 直接打接口拿到的，
标了「文档」的是对方公开文档原文。没有一条是估的。

## 一、钱：TikHub 便宜一半，但便宜的地方不在小红书

TikHub 有一个**公开、免鉴权**的按端点计价接口（实测可直接 GET）：

```
https://api.tikhub.dev/api/v1/tikhub/user/get_all_endpoints_info
```

拉下来 1401 个端点的单价。我们要用的那几个：

| 端点 | 单价 | 走量折扣 | 免费额度可用 |
|---|---:|:---:|:---:|
| `xiaohongshu/app_v2/get_note_comments` | **$0.010** | ❌ | ❌ |
| `xiaohongshu/app_v2/get_image_note_detail` | **$0.010** | ❌ | ❌ |
| `douyin/app/v3/fetch_video_comments` | **$0.001** | ✅ | ✅ |
| `douyin/app/v3/fetch_one_video` | **$0.001** | ✅ | ✅ |

对照 SocialDataX：**¥0.10/次，全平台一个价**（10 积分 × ¥0.01）。

两件事要划重点：

1. **小红书接口贵 10 倍于抖音**，而且 `allow_discount = 0`——
   你在官网看到的「日调用量 1000 起阶梯折扣」**对小红书接口不生效**。
   我们 65% 的调用量正好全压在小红书上，所以那个折扣基本白给。
2. **小红书接口 `allow_free_credit = 0`**，每日签到送的免费额度用不到它。
   想验一下都得先充钱。

### 按我们真实的分层刷新算（每天新发 20 条 / 小红书占 7 成 / 稳态在管 600 条）

| 档位 | 条数 | 刷新间隔 | 小红书调用/天 | 抖音调用/天 |
|---|---:|---:|---:|---:|
| 0–2 天 | 40 | 8h | 168 | 72 |
| 2–7 天 | 100 | 24h | 140 | 60 |
| 7–30 天 | 460 | 72h | 107 | 92 |
| **合计** | **600** | | **415** | **224** |

| | 每月 |
|---|---:|
| SocialDataX（639 次 × ¥0.10） | **¥1,918** |
| TikHub（415 × $0.01 + 224 × $0.001） | $131 ≈ **¥946** |
| 差额 | **省 ¥972/月（51%）** |

> 汇率按 1 USD = 7.2 CNY。差额对汇率不敏感，7.0～7.5 之间都是省 49%～52%。

**但省的钱是从哪来的，值得看清楚**：抖音那 224 次调用，
SocialDataX 收 ¥22.4/天，TikHub 收 ¥1.6/天——这一块 TikHub 便宜 **93%**。
小红书那 415 次，¥41.5/天 vs ¥29.9/天——只便宜 **28%**。

所以「省一半」这个总数，一多半是抖音贡献的。

## 二、活：小红书那一列，TikHub 没做承诺

这才是真正的决策点，不是价格。

我们的表要写回四样东西：评论数、置顶评论、前 N 条综合排序评论、失效/风控。
其中**置顶**（`是否置顶成功` / `置顶掉了` / `没有置顶`）只有小红书能判——
抖音接口本来就没这个字段，你自己也说过抖音不承诺置顶监控。

| | SocialDataX | TikHub |
|---|---|---|
| 响应 schema | **typed**，`is_pinned`、`comment_count` 等字段写在公开 OpenAPI 里 | **无字段约束**——评论接口的响应声明成一个通用 `ResponseModel`，`data` 是个空对象 |
| 错误契约 | **有编号**：1006 内容封控 / 1008 内容已删除（标注"不要重试"）/ 1007 临时不可用 | 无业务错误码表，失败信息以自然语言塞在 `data` 里 |
| 排序参数 | `default`（综合）可用 | `sort_strategy` 支持 `default`（文档标"不推荐"，见下） |
| 公开可读文档 | ✅ 免 Key 可拉完整 OpenAPI | ✅ 免 Key 可拉 OpenAPI，但关键字段没写 |

### 2.1 `is_pinned` 到底有没有——查不到，只能实测

TikHub 的小红书评论接口，OpenAPI 里响应是这样声明的：

```json
{"200": {"content": {"application/json": {"schema": {"$ref": "#/components/schemas/ResponseModel"}}}}}
```

`ResponseModel` 里只有 `code` / `request_id` / `message` / `time` 这些信封字段，
**`data` 里有什么，一个字都没写**。

TikHub 的接口是**上游原样透传**（参数就是抖音/小红书自己的 `aweme_id`、`cursor`、
`pageArea`），所以它**有可能比 SocialDataX 返回得更多**——归一化会丢字段，透传不会。
但也可能没有。这是个 50/50 的问题，读文档读不出来。

**验它只要 $0.01（约 ¥0.07）：**

```bash
export TIKHUB_KEY=你的key
python3 tools/probe_tikhub.py <你自己一条有置顶评论的笔记ID>
```

脚本会把 `data` 里所有字段路径铺平打出来，并高亮 `pin` / `top` / `stick` 的命中。

- **有** → TikHub 可以整套替换，每月省 ¥972
- **没有** → 小红书必须留在 SocialDataX，只把抖音搬过去

### 2.2 `sort_strategy="default"` 的"不推荐"，对我们不成立

TikHub 文档原文：

> `"default"`: 默认排序（不推荐，翻页时会丢失评论或重复抓取评论）

**理由是分页场景**。而我们**从不翻页**——一条笔记只取第一页，
拿评论总数 + 置顶 + 前 5~10 条给运营看氛围，看完就走。
分页游标会不会错乱，跟我们没关系。

所以这条不是功能倒退。反过来说，`latest_v2`（按时间倒序）**才是**功能倒退：
运营眼里的评论区是综合排序那一屏，置顶评论也是在那一屏出现的。

## 三、坑：三个 SocialDataX 没有、TikHub 有的

### 3.1 ⚠️ 传错笔记 ID 照样扣费（这条直接伤到"失效检测"）

TikHub 自己的接口文档写着：

> 如果传入错误或不存在的笔记ID（或分享链接解析失败），接口仍会正常响应，
> 但 `data` 中会返回上游"服务异常"信息，该请求 **同样会正常计费扣费**。

这跟他们定价页写的"失败请求不计费"是矛盾的，以接口文档为准。

**为什么这条要紧**：我们整个「已失效 / 风控中」的判定，靠的就是
SocialDataX 那套确定性错误码——`1008 content_deleted` 明确标了"不要重试"，
一次就能定罪；`1007 surface_unavailable` 是临时故障，重试即可。

换到 TikHub，帖子被删、帖子被封、上游抓取失败，**三种情况返回的东西长得一样**：
一句自然语言的"服务异常"，而且都扣钱。后果是：

- 每一条失效都要走满两击定罪（多花一轮调用）
- 真封控和上游抖动**永远区分不开**，`已失效` 这一列的准确度会掉
- 熔断阈值（一批里 >20% 失效就整批撤销写入）会被上游抖动误触发得更频繁

这不是致命伤，但 R5「帖子不在了要有提示」是你一开始就提的核心诉求之一，
换供应商就是拿它换钱。

### 3.2 ⚠️ 报错信息里会把你的 API Key 原样回显

实测（用假 Key 打的）：

```json
{"detail": {"code": 401,
  "message_zh": "无效的API令牌，您提交的API令牌为 fake-key-probe。..."}}
```

我们的 runner 会把错误文案写进飞书的「最后错误」列。照抄就等于**把 Key 写进表里**。
接 TikHub 的话，落库前必须先脱敏。SocialDataX 没这个问题。

### 3.3 ⚠️ Cloudflare 会按 UA 拦，主域名在大陆被墙

- **实测**：不带浏览器 UA 直接请求 → `HTTP 403 / error_code 1010 /
  browser_signature_banned`，连业务层都到不了。SocialDataX 裸 urllib 就能通。
- **文档原文**：`api.tikhub.io` 在大陆被防火墙拦截，大陆用户须改用
  **`api.tikhub.dev`**（实测该域名可用，同一套接口）。

对扣子方案的影响：扣子是境内的，出网得能到 `api.tikhub.dev`，
而且 `requests_async` 发出去的 UA 会不会被 Cloudflare 拦，**没有文档保证**。
这等于在原本就要做的连通性验证之外，又多一个未知数。

约 1 天工作量。**但别忘了改完要重新 `python3 tools/build_coze_node.py > coze_node.py` 并粘回扣子。**

## 五、我的建议

**分两步，不要一次全换。**

**第一步（现在就能做，无风险）：抖音搬去 TikHub。**
- 省 93%，而且抖音本来就没有置顶字段可丢，schema 无约束的风险对它小得多
- 抖音接口吃免费额度，可以签到白嫖着验
- 224 次/天 × ¥0.10 → ¥1.6/天，一个月从 ¥672 降到 ¥48

**第二步（先花 ¥0.07 验，再决定）：小红书。**
```bash
python3 tools/probe_tikhub.py <你的一条有置顶评论的笔记ID>
```
- 有 `is_pinned` → 全换，月省 ¥972，代价是失效检测变钝 + 要做 Key 脱敏
- 没有 → 留在 SocialDataX。小红书只便宜 28%（¥348/月），
  拿「置顶监控直接报废」换这个数，不划算

**双供应商是可以接受的**——`protocol.py` 本来就是按 (platform, purpose) 查表选端点的，
加一层"哪个平台走哪家"是自然的扩展，不是妥协。
