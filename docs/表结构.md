# 多维表格建表说明

列名必须与 `xhsearch/config.py` 里的 `FieldNames` **逐字相同**（含空格、括号全半角）。
飞书开放平台按**字段名**寻址，改列名会直接报 `1254045 FieldNameNotFound`。

如果你们表里已有同类列（比如已经叫「评论数量」而不是「评论数」），
**改 `config.py` 比改表更省事**——表里可能已经有历史数据和引用。

---

## 一、人工维护的列

| 列名 | 字段类型 | 必填 | 说明 |
|---|---|:---:|---|
| `链接` | **单行文本** | ✅ | 原样粘贴 App 里「复制链接」的整段分享文案即可，不用清理。**不要用超链接字段**——小红书链接带 `xsec_token`，超链接字段可能规范化掉它 |
| `发布时间` | 日期 | 建议 | 分层刷新靠它分档。留空则每轮都刷（宁可多花一毛，也别让一行永远不更新） |
| `种子评论关键词` | 单行文本 | 选填 | 置顶判定的锚点：种草评论里一段有辨识度的文本。**8–20 字最稳**；少于 4 字会被拒绝匹配（"券"这种会命中一大半评论） |
| `监控中` | 复选框 | ✅ | 取消勾选即完全停止刷新。结案后勾掉，永久止损 |
| `排队刷新` | 复选框 | ✅ | **手动触发入口**。勾上 → 后台处理 → 自动清掉。勾消失就是"已完成" |

> 为什么手动入口用复选框而不是按钮字段：复选框走后台轮询，**一次飞书自动化配额都不消耗**，
> 而且能拖拽批量勾 50 行。按钮每点一次消耗一次租户级配额，较低档位套餐只有 200 次/月。

## 二、机器写入的列

| 列名 | 字段类型 | 说明 |
|---|---|---|
| `平台` | 单选 | 选项：`小红书` / `抖音`。机器按链接域名识别 |
| `评论数` | **数字** | 小红书是含回复的笔记总评论数；抖音是作品总量 |
| `上次评论数` | 数字 | 写新值前先搬过来，用于算增量。建议在运营视图里隐藏 |
| `点赞数` | 数字 | 只在发布 7 天内补 detail 时才有 |
| `收藏数` | 数字 | 同上 |
| `置顶评论` | 多行文本 | 展示的是**实际置顶的那条**，不是我们希望置顶的那条。抖音行固定写「—（抖音不支持置顶监控）」 |
| `评论状态` | **多选** | 人机共用。机器管置顶三个值，人工维护的「评论是否显示」等值并列在同一列，机器不碰 |
| `评论区快照` | 多行文本 | 小红书是综合排序前 8 条；抖音是平台默认序前 8 条 |
| `流量状态` | **多选** | 人机共用，见下 |
| `刷新状态` | 单选 | 选项：`正常` / `疑似受限` / `已失效` / `刷新失败` / `跳过` / `冷却跳过` |
| `诊断信息` | 多行文本 | 人话解释 + 上游原始错误文本。运营看不懂也能截图给 IT |
| `最后更新时间` | 日期 | 失败也会更新——`刷新状态` 已经说明了数据新旧 |
| `连续失败次数` | 数字 | 两击定罪的计数器。建议隐藏 |

### `评论状态`（多选，人机共用）

和 `流量状态` 走的是同一套合并算法。机器只碰这三个值，**必须先建好**：

| 值 | 什么时候写 |
|---|---|
| `置顶成功` | 置顶的那条确认是我方种子评论 |
| `置顶掉了` | **之前成功过**，现在我方的置顶不在了 |
| `没有置顶` | 从来没成功过，现在也没有 |

三个值互斥，每轮只留一个。「置顶掉了」和「没有置顶」的区别全在**这一行的历史**：
读现值里有没有 `置顶成功` 或 `置顶掉了`，有就是掉了，没有就是从来没有。
掉了之后一直没恢复也会保持「置顶掉了」，不会退回「没有置顶」——那等于把曾经置顶过抹掉。

**「评论是否显示」这类人工维护的值放在同一列里就行**，机器读得到但永远不改。

有两种情况机器**完全不碰这一列**（保留原值，而不是清空）：

- **抖音行**：接口没有 `is_pinned`，判不了
- **没填 `种子评论关键词`**：有置顶但分不清是我方还是别人的，
  写「置顶成功」是撒谎，写「没有置顶」也是撒谎

**置顶被别人顶替**（置顶位还在，但换成了别人的评论）算「置顶掉了」——对我方而言置顶确实没了。
诊断信息里会写清楚「⚠ 置顶位被他人占据，我方评论掉到第 N 条」。这种情况往往比单纯掉置顶更急。

### `流量状态`（多选）

机器只碰这五个词，**必须在字段里先建好**：

| 标签 | 什么时候打 |
|---|---|
| `评估中` | 评论数 ≥ 20 |
| `爆贴` | 评论数 ≥ 50 |
| `大爆` | 评论数 ≥ 100 |
| `风控中` | 评论数腰斩 / 发布 48h 仍零评论 / 连续两次取不到内容 |
| `已失效` | 连续两次确认取不到内容（错误码 1008「已删除」第一次就判） |

**热度三档互斥且只升不降。** 一条帖子同时挂着三个没有意义，所以每轮只留最高的那个。
而且不会降档——评论被删导致数字掉下去，不该让一条帖子从「大爆」退回「爆贴」，
那种情况由 `风控中` 标签表达。要降档只能人工改。

`风控中` / `已失效` 是易变的，每轮重算，恢复正常会自动摘掉。否则表会越来越红，最后没人看。

**其余选项机器零权限**——`已复盘`、`客户确认`，以及你们未来新增的任何选项，
机器读得到但永远不会改。

> 没建的选项机器会跳过（不会误写，也不会让整批写入回滚），
> 但对应的判定就等于没生效。`python3 cli.py doctor` 会检查并列出缺哪些。

## 三、可选：增量公式列

建一个公式字段 `评论增量`：

```
评论数 - 上次评论数
```

飞书自己算，零写入成本，且公式列天然不可写。
**这是"今天谁涨得最猛"的排序列**，比看绝对值有用得多。

## 四、应用权限设置（最容易卡住的一步）

1. 飞书开放平台建**企业自建应用**，开权限 `bitable:app`，**发布版本并等审批通过**。
2. 打开目标多维表格 → 右上角 `…` → `更多` → **`添加文档应用`** → 搜应用名 → 添加。

   前置条件（搜不到应用时按顺序查）：操作人是文档所有者或有管理权限；
   应用**已发布版本**的可用范围包含文档所有者；应用**至少开通了一个云文档 API 权限**。

3. **如果这张表开了「高级权限」**：光加协作者不够，还要在高级权限里给这个应用 **「可管理」**。

   ⚠️ 漏这一步的表现是**读到空结果而不是报错**——最容易卡住半天。

4. `python3 cli.py doctor` 全绿再开跑。
