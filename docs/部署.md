# 部署：放在哪、怎么配、怎么跑起来

---

## 零、先做一个决定

这套东西要一直有个"东西"在定时跑。放哪取决于**一个问题**：

> 运营勾了「排队刷新」之后，最多能等多久？

| 能等 | 放哪 | 月成本 | 谁来配 |
|---|---|---:|---|
| **一小时** | GitHub Actions | **¥0** | 你自己，20 分钟 |
| **一分钟** | 一台国内小服务器 | ¥24–60 | 会用 SSH 的人，40 分钟 |

定时巡检（每 8 小时刷新帖的那条主线）两边都一样好，**差别只在手动勾选的响应速度**。

我的建议：**先上 GitHub Actions**。零成本零运维，仓库本来就在 GitHub 上，
配错了也不会有任何遗留物。跑一两周，如果运营真的抱怨"勾了半天没反应"，
再花 40 分钟搬到服务器上——业务逻辑一行都不用改，只是换个地方跑同一个命令。

> 关于扣子：能跑，但它是三个方案里唯一**没有版本管理、没法本地调试、
> 改代码要在网页 textarea 里改**的。而且它并不能让你少写 Python。
> 详见 [方案 C](#方案-c扣子工作流)。

## 一、通用前置（不管选哪个方案都要做）

### 1.1 SocialDataX 账号

去 <https://socialdatax.com> 注册 → 后台创建 API Key → 充值。

充多少：按 [`README.md`](../README.md) 的成本表，600 条帖子分层刷新约 **¥1,900/月**。
建议**先充 ¥100 试跑一周**，用真实数据核准了单价和刷新频率再按月充。

⚠️ Key 只显示一次，存好。它就是钱，泄露了别人能直接花你的积分。

### 1.2 飞书自建应用

1. 打开 <https://open.feishu.cn/app> → **创建企业自建应用**
2. 左侧「权限管理」→ 搜索并开通 **`bitable:app`**
3. 左侧「版本管理与发布」→ **创建版本 → 申请发布**（要等管理员审批通过）
4. 「凭证与基础信息」页记下 **App ID** 和 **App Secret**

### 1.3 把应用加进那张多维表格（最容易卡住的一步）

打开目标多维表格 → 右上角 `…` → `更多` → **`添加文档应用`** → 搜应用名 → 添加。

搜不到应用时按顺序查这三条：

- 操作人是不是文档所有者、或有管理权限
- 应用的**已发布版本**可用范围有没有包含文档所有者
- 应用有没有**至少开通一个云文档 API 权限**（没开通根本不会出现在搜索框里）

⚠️ **如果这张表开了「高级权限」**：光加协作者不够，还要进高级权限给这个应用 **「可管理」**。
漏这一步的表现是**读到空结果而不是报错**，最容易卡住半天。

### 1.4 记下表格的两个 ID

多维表格的地址长这样：

```
https://xxx.feishu.cn/base/bascnABCDEFG1234567?table=tblXYZ7890&view=vew...
                            └────────┬───────┘        └───┬────┘
                             FEISHU_APP_TOKEN      FEISHU_TABLE_ID
```

### 1.5 建列、建选项

照 [`docs/表结构.md`](表结构.md) 建好列。**两个多选列的选项必须先手工建好**，
机器不会自动创建：

- `流量状态`：评估中 / 爆贴 / 大爆 / 风控中 / 已失效
- `评论状态`：置顶成功 / 置顶掉了 / 没有置顶

## 二、先在本地跑通（5 分钟，强烈建议）

不管最终放哪，**先在自己电脑上跑一次 `doctor`**。它不花一分钱，
但能一次性验证权限、字段名、选项是否齐全——九成的"配好了跑不通"都卡在这里。

需要电脑上有 Python 3.11 或更高版本（`python3 --version` 查）。

```bash
git clone https://github.com/TangVarie/XHSearch.git
cd XHSearch
git checkout claude/xiaohongshu-screenshot-scraping-a72ctw

cp .env.example .env
# 用编辑器把 .env 里五个值填上

set -a && source .env && set +a
python3 cli.py doctor
```

全绿了再往下走。没绿就照它给的提示改——每条提示都写了具体怎么办。

然后可以试跑一行不花几毛钱：

```bash
python3 cli.py estimate          # 只算钱，不发请求
python3 cli.py row recXXXXXXXX   # 刷一行（record_id 在飞书里右键记录 → 复制记录链接，末尾那段）
```

## 方案 A：GitHub Actions（推荐）

**零服务器、零运维、免费。** 仓库已经在 GitHub 上，配置文件也已经写好了。

### A0. ⚠️ 先把 PR 合了

**GitHub 的定时任务只在默认分支上生效，`workflow_dispatch` 手动触发也要求
工作流文件已经在默认分支上。**

也就是说：这个 PR 合并之前，`Actions` 页面里根本看不到「刷新监控表」，
定时任务一次都不会跑，手动也点不了。这不是配错了，是 GitHub 的规则。

顺序必须是：**先合 PR → 再填 Secrets → 再跑 doctor**。

（合并之后如果还想在功能分支上试，可以在 `Run workflow` 的下拉里选分支——
但前提仍然是工作流文件已经在默认分支上存在过。）

### A1. 填 Secrets

打开仓库 → `Settings` → `Secrets and variables` → `Actions` → `New repository secret`，
建五个：

| 名字 | 值 |
|---|---|
| `SOCIALDATAX_API_KEY` | SocialDataX 后台复制的 Key |
| `FEISHU_APP_ID` | 飞书应用的 App ID |
| `FEISHU_APP_SECRET` | 飞书应用的 App Secret |
| `FEISHU_APP_TOKEN` | 表格地址里 `/base/` 后面那段 |
| `FEISHU_TABLE_ID` | 表格地址里 `table=` 后面那段 |

Secrets 存在 GitHub 这边，**不会出现在代码里**，也不会打印到日志里。

### A2. 先跑体检

仓库 → `Actions` 标签 → 左侧选「刷新监控表」→ 右上 `Run workflow` →
模式选 **`doctor`** → 跑。

这一步同时验证两件事：配置对不对，以及 **GitHub 的机器能不能连上飞书和 SocialDataX**
（它们的服务器在境外）。两个接口都是公网服务，正常应该能通，但这是必须亲眼确认的一条。

绿了再依次试 `estimate` → `queue` → `sweep`。

### A3. 定时任务已经配好了

`.github/workflows/refresh.yml` 里定了两条：

- **每小时**跑一次 `queue`——处理勾了「排队刷新」的行
- **每天 08:05 / 16:05 / 00:05（北京时间）**跑 `sweep`——分层巡检

改频率就改那个文件里的 `cron`。**改完必须合进默认分支才生效**（见 §A0）。

两个会让它悄悄停掉的坑：

- **定时任务默认是关的**，第一次要在 `Actions` 页面手动 `Enable workflow`
- **仓库连续 60 天没有任何提交**，GitHub 会自动停掉定时任务并发邮件通知。
  失败模式是静默的——表就是不更新了，没人会注意到。建议在日历上放一个季度提醒，
  或者干脆每季度推一个空提交

### A4. 关于免费额度

私有仓库每月 **2000 分钟**免费。按上面的配置估算：

```
每小时 queue：24 次/天 × 1 分钟（不足 1 分钟按 1 分钟算）= 720 分钟/月
每天 3 次 sweep：3 × 约 5 分钟 = 450 分钟/月
────────────────────────────────────────────
合计约 1170 分钟/月，在 2000 以内
```

**如果想把 queue 提到每 15 分钟**，就是 96 次/天 = 2880 分钟/月，**会超**。
那时候要么把仓库改成公开（公开仓库 Actions 不限量），要么就该搬去服务器了。

### A5. 这个方案的真实短板

**定时任务不准点。** GitHub 的 cron 高峰期会延迟十几分钟，偶尔整个跳过一次。
所以"勾了「排队刷新」之后多久有反应"实际是 **10–70 分钟**，不是"一小时整"。

对定时巡检完全没影响（8 小时一档，晚十几分钟无所谓）。
但如果运营的心理预期是"勾完去倒杯水回来就好了"，那这个方案会让人失望。

## 方案 B：一台国内小服务器（要秒回就选这个）

### B1. 买机器

腾讯云轻量应用服务器 / 阿里云轻量，**2核2G，Ubuntu 22.04**，约 ¥24–60/月。

**地域选香港或新加坡**，两个原因：不用备案（国内地域绑域名要备案，虽然这个方案
根本不需要域名，但省得以后麻烦），而且 SocialDataX 的服务器本身就在腾讯云香港，同城延迟低。

这个方案**不需要域名、不需要备案、不需要开任何入站端口**——它只往外发请求，
不接受任何外部访问。只留 SSH。

### B2. 装环境

SSH 上去，一路复制粘贴：

```bash
sudo apt update && sudo apt install -y python3 git
git clone https://github.com/TangVarie/XHSearch.git
cd XHSearch
git checkout claude/xiaohongshu-screenshot-scraping-a72ctw

cp .env.example .env
nano .env                    # 填五个值，Ctrl+O 保存，Ctrl+X 退出
chmod 600 .env               # 只有自己能读，.env 里是钱和密钥

set -a && source .env && set +a
python3 cli.py doctor        # 全绿再往下
```

### B3. 挂定时任务

```bash
crontab -e
```

粘进去（注意把 `/root/XHSearch` 换成你实际的路径，`pwd` 可以查）：

```cron
# 每分钟处理勾了「排队刷新」的行 —— 运营勾完最多等 1 分钟
* * * * * cd /root/XHSearch && set -a && . ./.env && set +a && /usr/bin/python3 cli.py queue >> /var/log/xhsearch.log 2>&1

# 每天 08:05 / 16:05 / 00:05 分层巡检
5 0,8,16 * * * cd /root/XHSearch && set -a && . ./.env && set +a && /usr/bin/python3 cli.py sweep >> /var/log/xhsearch.log 2>&1
```

⚠️ **cron 的环境变量和你 SSH 登录时不是一套**，所以每条命令都要自己 `. ./.env`。
这是 cron 任务"手动跑好好的、定时跑就不动"最常见的原因。

看日志：

```bash
tail -f /var/log/xhsearch.log
```

### B4. 别让日志把磁盘撑满

```bash
sudo tee /etc/logrotate.d/xhsearch > /dev/null <<'EOF'
/var/log/xhsearch.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
}
EOF
```

### B5. 每分钟跑一次会不会打架

不会。`queue` 模式只捞勾了「排队刷新」的行，没勾的时候它读一次表就退出，
几乎不耗资源，**也不花积分**（没有行就不发业务请求）。

但**如果上一轮还没跑完下一轮就起来了**，两个进程会同时写同一张表。
行数多的时候值得加个锁：

```cron
* * * * * cd /root/XHSearch && flock -n /tmp/xhsearch.lock -c 'set -a && . ./.env && set +a && /usr/bin/python3 cli.py queue' >> /var/log/xhsearch.log 2>&1
```

`flock -n` 的意思是"拿不到锁就直接退出"，不排队不等待。

## 方案 C：扣子工作流

你原本倾向这个。它能跑，但先把三件事说清楚：

1. **它不能让你少写 Python。** 600 行不能展开成工作流节点（会撞节点执行上限），
   循环必须写在代码节点里。所以逻辑还是这套 Python，只是住的地方不同。
2. **代码节点硬上限 60 秒。** 600 行必须切成 15 块，靠定时触发器一轮轮排干，
   约 30 分钟跑完。服务器上是一口气 7 分钟。
3. **没有版本管理、没法本地调试。** 改代码在网页 textarea 里改，
   出错只能在网页运行记录里翻。

如果这三条你都接受（比如公司规定不能自己买服务器），步骤：

### C1. 生成粘贴用的单文件

```bash
python3 tools/build_coze_node.py > coze_node.py
```

这个文件是从 `xhsearch/` 下的源码**自动生成**的，所以判定口径和服务器版永远一致。
改了逻辑要重新生成一次，别手改生成物。

### C2. 建工作流

1. <https://www.coze.cn> → 建一个工作流
2. **开始节点**入参（全部 String）：`mode` / `record_ids` / `api_key` /
   `app_id` / `app_secret` / `app_token` / `table_id`
3. 加一个 **代码节点**，语言选 Python，把 `coze_node.py` 整个粘进去
4. **结束节点**出参：`ok`(Boolean) / `processed`(Number) / `credits`(Number) /
   `balance`(Number) / `message`(String)
5. 挂**定时触发器**，每 2 分钟一次

### C3. 上线前必须先验这一条

**扣子的代码节点能不能连上 `mcp.socialdatax.com`，没有任何文档保证。**
出网白名单也没见文档。这一条不通，整个扣子方案当场作废。

验法（不花钱）：建一个只有 1 个代码节点的工作流，用**假 Key** 打一次：

```python
import requests_async as requests

async def main(args):
    r = await requests.post(
        "https://mcp.socialdatax.com/socialdatax/api/v1/xhs/note/comment/list",
        headers={"Authorization": "Bearer fake", "Content-Type": "application/json"},
        data=b'{"note_id":"x"}', timeout=20)
    return {"status": getattr(r, "status_code", 0), "body": r.text[:200]}
```

**返回 401 就是通了**（说明请求抵达了对方的业务层）。超时或连接错误就是出网受限。

顺便确认 `r.text` 拿得到完整内容、`r.headers` 能读——代码里要用这两样。

## 三、上线第一周该盯什么

1. **每天看一眼积分余额**。刷新报告最后一行会打印余额。
   烧得比预期快，就调 `config.py` 里的 `RefreshTiers`（把老帖的间隔拉长最省钱）。
2. **收集「诊断信息」里的怪话术**。笔记被删/被封控实际会命中哪个错误码
   （1003 / 1006 / 1008），只有真数据能告诉你，见 [`docs/待验证清单.md`](待验证清单.md)。
3. **看爆贴阈值准不准**。20 / 50 / 100 是拍的，跑一周拿真实分布回来调。
   改 `config.py` 里的 `Thresholds` 就行，不用动别的。

## 四、排错

| 症状 | 多半是什么 |
|---|---|
| `doctor` 卡在第 ① 步 | app_id / app_secret 填错，或应用还没发布通过审批 |
| `doctor` 说读不到字段列表 | 没做 §1.3「添加文档应用」，或高级权限没给「可管理」 |
| 读到 0 行但表里明明有数据 | 高级权限没给应用「可管理」（表现是空结果不是报错），或者没有行勾了「监控中」 |
| `1254045 FieldNameNotFound` | 列名和 `config.py` 对不上，差一个空格也不行 |
| `1254060` 字段类型不对 | 数字列被写了字符串，或日期列没给毫秒时间戳 |
| 某些标签一直不出现 | 那个选项在多选字段里还没建。`doctor` 会列出缺哪些 |
| 手动跑好好的、定时跑不动 | cron 没有加载 `.env`，见 §B3 |
| 表里一片「疑似受限」 | 先别慌。看诊断信息里的 request_id 和错误码；如果是整批出现，熔断已经拦住了标签写入 |
| 抖音行的「置顶评论」永远是那句话 | 这是对的。抖音接口没有 `is_pinned`，判不了 |
