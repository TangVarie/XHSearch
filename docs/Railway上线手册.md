# Railway 上线手册

从零到跑起来，一步一步。**预计 60–90 分钟**，其中一半时间在等飞书管理员审批。

不需要写代码，不需要懂 Python。每一步都写了「做完应该看到什么」，
对不上就停下来看那一步末尾的「卡住了怎么办」。

---

## 为什么是 Railway 不是扣子

| | Railway | 扣子 |
|---|---|---|
| **双通道能不能真的用上** | ✅ 已实测两条都通 | ⚠️ **TikHub 那条可能用不了**，见下 |
| 跑的代码从哪来 | ✅ 直接连 git 仓库 | ⚠️ 网页里粘贴的副本 |
| 单次执行上限 | 无 | 60 秒（600 行要分 15 轮、约 30 分钟排干） |
| 能不能跑体检（`doctor`） | ✅ 能 | ❌ 不能 |
| 勾选后多久有反应 | 5–10 分钟 | 1–2 分钟 |
| 每月增量成本 | 约 $0.1 | 走会员额度 |

**决定性的一条**：TikHub 挂在 Cloudflare 后面，请求必须带浏览器 `User-Agent`，
否则直接 403（实测踩过）。扣子的 `requests_async` 允不允许覆盖这个请求头，
**没有任何文档保证**。如果不允许，扣子上就只剩 SocialDataX 一条通道——
那恰恰把「怕通道不稳定」这件事变成了没法解决的问题。

Railway 上用的是标准库，请求头想怎么设怎么设，已经实测跑通。

代价是勾选后要等 5–10 分钟而不是 1–2 分钟（Railway 的 cron 最小间隔就是 5 分钟）。
对「看评论区氛围、判爆文、发现风控」这些事，这点差别不影响任何决策。

## 一、把代码放进你自己的仓库

现在这个仓库不适合长期维护，所以第一步是搬家。**搬完之后所有更新都在新仓库里做。**

### 1.1 建一个空仓库

GitHub → 右上 `+` → `New repository`

- **Repository name**：随便起，比如 `note-monitor` / `xhsearch`
- **Visibility**：选 **Private**（代码里不含密钥，但没必要公开）
- 下面的 `Add a README file` / `.gitignore` / `license` **三个都不要勾**——
  勾了会产生一个初始提交，等下推代码要多解决一次冲突

建完它会给你一个地址，形如 `https://github.com/你的用户名/note-monitor.git`，**复制下来**。

### 1.2 把代码推过去

在你自己电脑上（需要装了 git）：

```bash
# 1. 把现在这份代码拉下来
git clone https://github.com/TangVarie/XHSearch.git note-monitor
cd note-monitor
git checkout claude/xiaohongshu-screenshot-scraping-a72ctw

# 2. 抹掉旧仓库的历史，重新开始
#    （这份代码是一路探索出来的，几十个提交对新仓库没有价值，
#      而且旧仓库里还有别的分支和一堆 skill 文件）
rm -rf .git
git init -b main
git add -A
git commit -m "小红书/抖音笔记评论监控，回写飞书多维表格"

# 3. 推到你的新仓库（把地址换成 1.1 里复制的那个）
git remote add origin https://github.com/你的用户名/note-monitor.git
git push -u origin main
```

**做完应该看到**：GitHub 上刷新，能看到 `xhsearch/`、`cli.py`、`docs/` 这些文件，
提交历史只有一条。

> **卡住了怎么办**
> - `git push` 要求登录 → GitHub 现在不收密码了，要用 Personal Access Token
>   （Settings → Developer settings → Personal access tokens → 建一个勾 `repo` 权限的），
>   push 时用户名填你的用户名、密码栏粘那个 token。
> - 提示 `rejected ... fetch first` → 你在 1.1 勾了 README。
>   跑 `git push -u origin main --force` 覆盖掉那个初始提交即可（新仓库里没东西可丢）。

### 1.3 确认测试是绿的

```bash
python3 -m unittest discover -s tests -t .
```

**做完应该看到**：`Ran 192 tests ... OK`，两秒内跑完。
这一步不需要任何密钥、不联网、不花钱。跑不通就是 Python 版本太老
（需要 3.11+，`python3 --version` 查一下）。

## 二、两个数据通道

### 2.1 TikHub（主通道）

1. <https://user.tikhub.io> 注册 → **验证邮箱**（不验证不能用）
2. 用户中心 → API 令牌 → 创建 → **立刻复制存好，只显示一次**
3. 充值。支付页选「信用卡/借记卡」，**银联卡可以直接付，不用注册 PayPal**；也支持 USDT

**充多少**：600 条帖子分层刷新约 $131/月。**建议先充 $20 跑一周**，
用真实账单核准了再按月充。

> ⚠️ 每日签到送的免费额度**用不到小红书接口**，想验小红书必须先充钱。抖音接口可以白嫖。

### 2.2 SocialDataX（备胎）

1. <https://socialdatax.com> 注册 → 后台创建 API Key → 复制存好
2. **充 ¥50 就够**

它单价贵一倍，平时一分钱不花——只有 TikHub 网络故障 / Key 失效 / 余额见底时才顶上。
留着它的理由是它的错误码有契约（`1006` 封控 / `1008` 已删除），判失效比 TikHub 准。

> **只想先用一家？** 可以，另一个环境变量留空即可，代码会自动把没配 Key 的通道滤掉。
> 但那样就没有降级能力——半夜 Key 失效或余额见底，就是一整晚的监控全丢。

## 三、飞书那边

**这一节最容易卡住，而且卡住的表现是「读到空结果而不是报错」**，所以每步都要确认。

### 3.1 建自建应用

1. <https://open.feishu.cn/app> → **创建企业自建应用**，名字随便起
2. 左侧「凭证与基础信息」→ 记下 **App ID** 和 **App Secret**
3. 左侧「权限管理」→ 搜 `bitable` → 开通 **`bitable:app`**（多维表格读写）
4. 左侧「版本管理与发布」→ **创建版本 → 申请发布**

**做完应该看到**：版本状态变成「已发布」。

> **卡住了怎么办**：状态卡在「审核中」= 要等管理员批。这一步没法绕过，
> 提前跟管理员打招呼能省半天。

### 3.2 ⚠️ 把应用加进那张表（最容易漏的一步）

**权限开了不等于能访问你那张表。** 还要在表里单独授权：

打开多维表格 → 右上角 `···` → **更多** → **添加文档应用** → 搜你刚建的应用名 → 添加 → **权限给「可编辑」**

**做完应该看到**：应用出现在协作者列表里，权限是「可编辑」。

> **漏了这一步的表现**：`doctor` 能取到 token、也能列字段，但**读记录读到 0 行**，
> 不报任何错。看到「读到 0 行」第一反应就该是回来检查这里。

### 3.3 建列和选项

照 [`表结构.md`](表结构.md) 建好列。**两个多选列的选项必须手工先建好，机器不会自动创建**：

- `流量状态`（多选）：`评估中` / `爆贴` / `大爆` / `风控中` / `已失效`
- `评论状态`（多选）：`置顶成功` / `置顶掉了` / `没有置顶`

⚠️ 两列都必须是**多选**类型。如果是单选，「加标签不覆盖人工值」这个需求技术上就不成立。

⚠️ 列名要和 `xhsearch/config.py` 里的**逐字一致**，差一个空格飞书就报
`1254045 FieldNameNotFound`。你们表里叫别的名字就去改 `config.py`，那是唯一需要改的文件。

### 3.4 记下表格地址里的两段

表格地址长这样：

```
https://xxx.feishu.cn/base/bascnABC123DEF?table=tblXYZ789
                            └── app_token ─┘       └ table_id ┘
```

用编辑器打开 `.env`，填这几个：

## 五、Railway

### 5.1 建项目

<https://railway.com> → `New Project` → **`Deploy from GitHub repo`** → 选你的新仓库

第一次用要授权 Railway 访问你的 GitHub。选仓库时如果列表里没有，
点 `Configure GitHub App` 把新仓库加进可访问范围。

**做完应该看到**：它自动开始构建，几十秒就完。
（仓库里那个空的 `requirements.txt` 就是给它认「这是 Python 项目」用的，别删。
这个项目零第三方依赖，没有东西要装。）

### 5.2 填环境变量（项目级，两个服务共用）

项目页 → `Variables`（**项目级的，不是服务级的**，这样建第二个服务时不用再填一遍）

| 名字 | 值 |
|---|---|
| `TIKHUB_API_KEY` | TikHub 令牌 |
| `SOCIALDATAX_API_KEY` | SocialDataX Key |
| `TIKHUB_BASE` | **`https://api.tikhub.io`** ← 见下 |
| `FEISHU_APP_ID` | 飞书 App ID |
| `FEISHU_APP_SECRET` | 飞书 App Secret |
| `FEISHU_APP_TOKEN` | 表格地址里 `/base/` 后面那段 |
| `FEISHU_TABLE_ID` | 表格地址里 `table=` 后面那段 |

> **`TIKHUB_BASE` 为什么要填**：TikHub 有两个同功能的域名，
> `api.tikhub.dev` 给境内、`api.tikhub.io` 是主域名，对方文档明确要求
> **「请勿跨区使用，会影响访问速度」**。Railway 的机器在境外，所以要切到 `.io`。
> 代码默认取 `.dev`（境内境外都通），不填也能跑，只是慢一点。

### 5.3 先在 Railway 上跑一次体检

Service → `Settings` → `Deploy` → **Start Command** 填：

```
python3 cli.py doctor
```

点 `Deploy`，然后看 `Deployments` → 日志。

**做完应该看到**和本地一样的四段全绿。这一步额外验证了一件本地验不了的事：
**Railway 的机器能不能连上飞书**。

### 5.4 改成两个定时服务

Railway 的 cron 是**一个服务一个调度**，所以要两个服务，都连同一个仓库。

**服务一 · 处理勾选**（就是刚才那个，把 Start Command 改掉）

| 设置项 | 值 |
|---|---|
| Start Command | `python3 cli.py queue` |
| Cron Schedule | `*/5 * * * *` |
| Restart Policy | **`Never`** ← 别忘 |

**服务二 · 分层巡检**（项目页 → `+ New` → `GitHub Repo` → 选同一个仓库）

| 设置项 | 值 |
|---|---|
| Start Command | `python3 cli.py sweep` |
| Cron Schedule | `5 0,8,16 * * *` |
| Restart Policy | **`Never`** ← 别忘 |

`5 0,8,16 * * *` 走 UTC，对应北京时间 **08:05 / 16:05 / 次日 00:05**。

### 5.5 ⚠️ Restart Policy 一定要设成 `Never`

**这是这套部署里最能烧钱的一个坑。**

定时任务跑完就退出，而 Railway 默认的重启策略是 `On Failure`。
哪天 Key 过期、余额耗尽，程序退出码非零，Railway 会**反复重启它**——
变成一个高频循环，一晚上能烧掉不少钱，而且每一轮都在打上游接口。

设成 `Never` 就没这回事。

（代码这边也做了配合：只有真故障才返回非零。到软截止把剩余的行留给下一轮
属于正常运行，返回 0，不会触发重启。）

### 5.6 另外三个要知道的 Railway 行为

- **cron 最小间隔 5 分钟**，而且启动会漂移几分钟，所以勾选后的实际体感是 **5–10 分钟**。
- **上一轮没跑完，下一轮直接跳过。** Railway 不让两个实例并行——这正好帮我们避免了
  两个进程同时写一张表。`queue` 每轮只处理到期的行，几秒就完，撞不上。
- **cron 走 UTC**，北京时间减 8 小时。

### 5.7 要花多少钱

Railway 按「资源 × 分钟」计费，**内存通常是账单里最大的一项**。

实测这个服务的峰值内存 **28 MB**（600 行时；解释器加全部导入的基线是 24.5 MB），
纯计算耗时 0.18 秒——绝大部分时间在等网络，不吃 CPU。

| 项目 | 用量 | 费用 |
|---|---:|---:|
| Memory | 约 6–12 万 MB·min | $0.01–0.03 |
| vCPU | 约 2,000–4,000 vCPU·min | $0.01–0.02 |
| Network | 约 0.7 GB | $0.04 |
| **合计** | | **约 $0.1/月** |

> **别把它改成「起一个进程自己 sleep 循环」。** 常驻进程是 24×30 天 = 43,200 分钟
> × 28 MB ≈ 121 万 MB·min ≈ $0.28/月；cron 只在跑的时候计费，便宜十倍。

真正的成本大头是**数据接口**（约 ¥950/月），不是 Railway。

## 六、跑起来之后

### 6.1 每天看一眼

刷新报告最后一行长这样：

```
处理 40 行（正常 38，疑似受限 2），花费 ≈ ¥2.88（tikhub 68 次）
```

出现降级时会多一句：

```
花费 ≈ ¥3.10（socialdatax 12 次、tikhub 56 次），其中 12 次是主通道失败后降级完成的
```

> **降级次数持续不为 0 就说明主通道有问题。** 那时候还在正常出数，
> 只是因为备胎在扛——别等备胎也倒了才发现。去 TikHub 后台看余额和公告。

### 6.2 表里出现这些状态是什么意思

| 刷新状态 | 含义 | 要不要管 |
|---|---|---|
| `正常` | 取到数了 | 不用 |
| `疑似受限` | 第一次取不到内容，**只计数，一个标签都没打** | 观察，下一轮会复核 |
| `已失效` | 连续两次取不到 → 打上 `已失效` | 人工确认一下是不是真被删了 |
| `刷新失败` | 网络/接口故障，**已有数据一个都没动** | 看「诊断信息」列 |
| `冷却跳过` | 90 秒内刚刷过，没花钱 | 不用 |

诊断信息里如果出现 `⚠ 上游把这条标成了审核中/受限，请人工确认`——
那是上游自己的审核标记。**它不会自动打「风控中」标签**，因为这个字段还没在
真被封的帖子上验过。看到就人工去平台确认一下。

### 6.3 熔断

一批里判失效的比例超过 20%（且样本 ≥ 10 行），**整批撤销标签写入**，
报告里会打 `🛑 已熔断`。

几百条笔记不可能在同一小时被集体删除，出现这个一定是上游挂了。
这一轮什么都不写是对的，不用管，下一轮自然恢复。

### 6.4 以后怎么改

改 `xhsearch/` 下的代码 → `git push` → **Railway 自动重新部署**。
不用登面板，不用粘贴任何东西，**跑的永远是仓库里那一版**。

最常改的是 `xhsearch/config.py`：列名、爆文阈值（20/50/100）、
分层刷新间隔、快照里显示几条评论。改完 `git push` 就生效。

改判定逻辑记得跑一遍 `python3 -m unittest discover -s tests -t .`——
192 个测试全离线，两秒跑完，能挡掉绝大部分改坏的情况。

## 附：出问题时按这个顺序查

| 现象 | 先查这里 |
|---|---|
| 表一直不更新 | Railway → Deployments 日志。有没有在跑？Cron 配了吗？ |
| 日志说读到 0 行 | **§3.2 忘了把应用加进表**，九成是这个 |
| `1254045 FieldNameNotFound` | 列名和 `config.py` 对不上，差空格也算 |
| 报错里有 `auth` | Key 填错或过期。TikHub 和 SocialDataX 分开看是哪个 |
| 报错里有 `transport` | 网络。TikHub 确认 `TIKHUB_BASE` 设成了 `.io` |
| 报错里有 `quota` | 余额见底。有备胎的话它会自动顶上，但要去充值 |
| 标签被机器覆盖了 | 不该发生——机器只碰它自己那几个值。真遇到请把那一行的截图留着 |
| 一堆行突然变「已失效」 | 看有没有打 `🛑 已熔断`。打了就是上游故障，不用管 |

日志里每条错误都带 `request_id`，找供应商排查时把它发过去就行。
